# Alternative Weapons Control - dev notes (for Claude)

Condensed 30.10 (version 1.3.0): current design and decisions only. The long history (Russian, step-by-step traces, abandoned attempts) is in git: `git show b475635:DEVNOTES.md`.

Sea Power mod: a Weapons tab in the Unit Status window (own ships and submarines, ground units, aircraft): launchers, targets, ammunition, fire-control channels, per-domain auto engagement switches, Fire / Cease fire / Reload; gun fixes; SAM readiness. BepInEx 5 + Harmony, loaded through Anchor Chain (Workshop 3380210757). Built like Alternative Damage Model: settings = gear on the tab button, legend = (i). Game access by reflection (class `R` in WeaponsModel.cs: fields/properties of any visibility, methods by name with overload matching, type -> name -> member caches); Noesis is referenced directly.

## Compatibility
`_info.ini` ApproximateVersion=0.8.6; 0.8.7 supported. A missing game member = soft failure of that feature (warning in the log). Specifics for 0.8.7:
- `WeaponSelector.GetWeaponSystemsForAmmunition` has a 5-parameter overload `(obj, pos, ammoId, target, List vwsList) : bool` that nearly all calls use; exactly one is patched (new if present: `SelectorPostfix5`, else `SelectorPostfix`), logic in `SelectorCore`.
- `MissileSimulator.GetAccelerationTimes` has two overloads: `GetMethod` by argument types.
- `WeaponSystem.targetIsInFiringArc` is virtual; the CIWS override calls base only for surface units.
- The 2D firing wedge is drawn by `WeaponArcSegmentViewModel.Render` (see Zones).
- Obsolete duplicate files must not return to the repo (`Diagnostics.cs`, `Flash.cs`, `Optics.cs` were deleted).

## Model (WeaponsModel.cs)
- Launchers = `_obp._weaponSystems` (index = settings key) without Chaff / Noisemaker / Hardpoint(except aircraft) / UNKNOWN; name = `DisplayName.Value`; ammunition = `_associatedAmmunitionNames`. Section by `_weaponType` (CIWS, Gun) and the first ammunition (AAW -> SAM; ASuW -> ANTI-SHIP; ASW / RBU / ASROC / torpedo vs submarines -> ASW; surface-only torpedo -> ANTI-SHIP; land strike only -> LAND ATTACK; `AmmoDomains` drops the surface domain when `_canNotAttackTypes` has Vessel and the ammunition has `_landAttack`, e.g. Tomahawk RGM-109C: TargetType=ASuW but land only -> LAND ATTACK). Group = section + name + ammunition set (x N). The group title (the draggable section card header, `MakeTitle` / `TitleText`, refreshed in `Refresh` so the option acts at once; `[UI] SectionTargetTypes`, off, only for the extras of SAMs) gets "/" + the other purposes of the ammunition of its launchers ("ANTI-SHIP/ASW" for SS-N-14b: ASuW + secondary ASW; "SAM/ANTI-SHIP" for a SAM with a secondary target; pure AAW: just SAM; a torpedo has one purpose; per-ammo domains `AmmoDom`; sections 0-3 only). The group names are not changed. Stock: a gun with a magazine counts the magazine only (the mount's `_sharedLoadedAmmoCount` is part of it); a launcher row with a magazine of its own shows the magazine's rest, not the mount's rounds (shared magazine: own rounds).
- Location label: world position of `_containers[0]._gunObject` (else `_mountObject`); fore/aft by z, port/starboard by x only if |x| > 0.02 units (and > 25% of max). Launchers of the same name standing at one point (spread < 0.03 units) use the centre of `_vwp._preferredArcs[0]` (0 fore, 180 aft, +-90 port/starboard). Same labels get "#N"; a part common to all launchers of a name is dropped ("Fore port / Fore starboard" -> "Port / Starboard"). A single-launcher group whose name equals another group of the section gets the location (or #N) appended (`GroupRow.Suffix`).
- Domains: AIR, MSL (missiles and torpedoes as targets), SUR (ships, surfaced subs), SUB, LND. Launcher domains = union over its ammunition (AAW -> AIR+MSL, ASuW -> SUR, ASW -> SUB, `_landAttack` -> LND, `_antiTorpedo` -> MSL).
- Player switches: `UnitW.Off[index]` = mask of switched-off domains (ConditionalWeakTable per unit), saved in the unit's save section (`AlternativeWeaponsControl_WeaponAuto=idx:mask,...`; postfixes of ObjectBase.Save/LoadStateFromFile).
- Standing Orders merge (`TacticalDoctrine`): AutoAttackSurface, ShipsAutoUseSAMsAgainstSurfaceTargets, ShipsAutoUseAntiShipMissilesAgainstSurfaceTargets. Chip colours: grey = off by player, yellow = forbidden by orders, green = auto, "mixed" half-circle for a group. Enabling something forbidden by orders sets the unit item to Yes and switches off the other pairs that this turned on; disabling only sets the player's Off. A change of orders from outside is detected by a snapshot of ResolvedValue (`SyncDoctrine`).
- Aircraft / helicopters: ONE `WeaponSystemHardpoint` (many Stations); ammunition of several types in `_associatedAmmunitionNames`; a Hardpoint is one Launcher (section STORES; fuel tanks, buoys skipped); switches act on the whole hardpoint by TARGET domain. Ground units (`LandUnit`) behave like ships except the AutoAttackSurface item and the Tight row.
- Stock: max = `_initialAmmoCount` of magazines (each once) + `_maxAmmoCount` of launchers without a magazine; `Cap(ws)` uses the rail slot count when `_maxAmmoCount` is 0 (Mk 141); aircraft guns with `_maxAmmoCount >= 10000` and a magazine show Stock/StockMax; "/10000" is cut from the game status text (`StatusParts`). Rails line "on launcher N/M" for single non-gun launchers with rails.

## Auto engagement (WeaponsAi.cs)
- "Automatic" = inside AI.OnUpdate / OnFixedUpdate, or inside ObjectBase.HandleEngageTasks for tasks with `_isAutoAttack`. Postfix of `GetWeaponSystemsForAmmunition` removes launchers switched off for the target's domain (new list). Manual fire is not filtered.
- CIWS: prefix `WeaponSystemCIWS.AquireTarget` drops a current target of a forbidden domain and collects positions of forbidden objects; postfix `targetIsInFiringArc` returns false there. `CiwsEnter` also puts plot contacts of switched-off domains into the skip set.
- Finalizer of HandleEngageTasks: the game hands a task to all guns / CIWS with the same ammunition; an auto task on a launcher switched off for the domain is ended (`EndEngageTask`).
- `R.F` does not see properties: `ObjectBase._taskforce` is a property, use `R.V` (field or property).

## Per-launcher target (Fire pin)
- Fire / arrow on a launcher sets `Pending` (unit, launcher, ammunition). A click on a target creates an AttackTask order at once (also on pause); the EngageTask appears when the order executes: postfix `AttackingState.AddAttackTask` binds the new order to the launcher (`OrderPins`), postfix `AttackTask.OnExecute` passes the pin to the task (`Pins`). Pending lives while the game's AttackingState of the unit exists, +3 s (30 s if targeting never started).
- Selector: a task with a pin is offered only its launcher. The game hands a new task to ALL guns with the same shell: prefix HandleEngageTasks remembers the firing fields of all systems (`EngageFields`), the finalizer restores them for systems that got a foreign pinned task (else EndEngageTask). "Breaks off" is blocked: `_hetPin` marks the current pinned task and the prefix of `WeaponSystem.EndEngageTask` inside HandleEngageTasks skips it for all systems except the pinned launcher. Several pinned tasks in one hand-out: `HetEnter` remembers them (`_pinnedIn`), `HetLeave` puts back those that are not in the list and not on their launcher.
- Save: the game writes `<unit>EngageTask1..N`; the mod writes `AlternativeWeaponsControl_PinTasks=N:launcherIndex,...` (the old `_Pins=UID:index` is still read). Game bug: a task whose target is created after the unit (units load one by one) becomes a task at point (0,0,0); `FixTargets` / `FixTargetsStep` recreate such tasks in the first frames (up to 300 s) for all tasks, whatever the mod tick.
- Limits: a salvo bigger than the launcher's stock does not move to another launcher; a target outside the sector will not be fired at; orders from the bottom panel do not select a launcher. Open (not changed): the game keeps only launchers whose preferred arc holds the target, so a pin outside that subset is not offered ("the pinned one is NOT among them" in the trace); possible fix: put the pin back if it passes the game's own filters.

## Fire-control channels
- Directors = `_vwp._associatedSensors`. Needed only if `ObjectBase.DoesEngageRequiresSensor(ap, target)` (projectiles, SARH, command guidance). Only radar directors (`SensorSystemRadar`) limit: a director (operable, on or `_autoEnableSensor`, `CanGuideAmmo`) with a free T (or already aimed at this target) and a free W (`_associatedWeapons.Count < EffectiveWeaponChannels`). Sonar / optics are not limited. Wire-guided torpedoes: "Wires x/y".
- Counter frame in the group row: "T used/total . W used/total" by unique radar directors of the group, yellow when T or W is exhausted; hovering opens a directors window in the `v.Overlay` Canvas (name = encyclopedia link, on/off/damaged, live channels, key facts). The pinned task waits as "Queued" / "Waiting for FCR channel" (`Cat` 5) until its first shot; cancel with the stop button.
- Guns / CIWS do not wait: `WeaponSystemGun.SetTarget` tries `TryToAddTarget`; accuracy by `GetFireControlSensor()` = best working director (`FireControl.ResolveBestDirector` for CIWS) with its `_fcSolutionGainRate`; without a working director: local control (`Globals._gunLocalControlGainRate` 0.6, error x(1+2*darkness)). Mark next to the weapon name: the director in blue, or "Local control" in orange.
- `GunChannelLimit` (false): postfix `WeaponSystemGun.GetFireControlSensor` (guns only): the chosen director not holding the target -> another working one that holds it; else `TryToAddTarget` on each call; failing -> null (local control). `GunOneDirector` (true): the game's `WeaponSystemGun.activatePreLaunchGuidance` calls `TryToAddTarget` on ALL directors of the gun; the prefix remembers each director's state, the postfix keeps the target on one (the previous holder, else the best new radar with the larger `_fcSolutionGainRate`) and restores the rest. Both options apply to guns only (`WeaponSystemGun`, weapon type "Gun"); CIWS and machine guns are not touched.

## Ships: chasing ([Ships])
`AlignUnitToTarget.GetValidHeadingArcs` sets `_goingIntoFiringRange` and a +-2 degree arc when the target is out of range. `NoRbuSurfaceChase` (true) / `NoAirChase` (true): postfix `ChasePostfix` sets `_goingIntoFiringRange = false` and no arcs (the ship keeps its course) when the target is farther than max range and is surface with RBU ammunition, or air (aircraft, helicopters, missiles). Turning away from a too-close target is vanilla.

## Guns (GunFixes.cs, AmmunitionFix.cs)
- `AimBeyondMaxRange` (true): `WeaponSystemGun.AlignTurret` returns at once beyond `_launchRangesInUnity.y`. Prefix (player's units): if max < dist <= `AimLimit` = max(1.5*max, 5 nm), `targetPosition` is replaced by a point at the same azimuth at 0.98*max; postfix forces `__result = false` (no fire). Air targets: max is capped at `DirectFireRangeUnity*1.15`. CIWS and machine guns: prefix `WeaponSystemCIWS.FireAtTarget` (`CiwsAimPrefix`, class `SeaPower.WeaponSystemCIWS`, not `SeaPower.CIWS`) in the zone (max + CiwsPrepMargin, limit] aims with `CalculateAimPosition` + `alignToTarget(aim,false,0,false)` and skips the original. Launchers are not covered. Outside the firing sector: guns need no patch (`RotateMountTowardsTarget` goes to the nearest edge of the sector, `_engageOnlyInsideArc` weapons are not offered the target by the selector at all); `CiwsAimPrefix` also takes over when the target is outside the horizontal / vertical sector (vanilla `FireAtTarget` only stops the fire there): `StopFire`, then `alignToTarget` (`WeaponSystemCIWS` derives from `WeaponSystemGun`, so the same rotation code runs); the option is labelled "Aim guns at targets beyond max range". `[Guns] EngageOutsideSector` (true): postfix of `IniHandler.readValue(string,string,bool,bool)` returns False for key `EngageOnlyInsideArc` (read once per weapon when a unit is loaded: applies to units loaded after the change, player and AI alike), so the selector / `HandleEngageTasks` no longer drop out-of-sector targets for those weapons.
- `MaxAccuracyMeters` (hint "game: ~40"): `GetMeasurementRangeSigma` = max(`Globals._gunFCBaseRangeErrorFloorUnity` (0.595 units ~ 40 m), 1.5% of range) / gain^2 * lighting * (1-0.7*solution). The constant floor is the fire-control error and dominates up to ~1.4 nm. The option replaces the floor for the call (`RangeSigmaPrefix` / `Finalizer`); 1 unit = 0.036285132 nm.
- `AccuracyMultiplier` (1, GUI Guns tab, group Accuracy): global; in the same constructor postfix (`AmmoFixPostfix`, works with `AmmunitionFix` off too) the game's `_circularErrorProbable` of projectiles is divided by it (2 = twice as accurate) BEFORE the pack's / the player's CEP replaces it as is (those are not multiplied). Same timing: ammunition loaded after Apply.
- `FireControlAccuracy` (1, GUI Guns tab, group Accuracy): postfix of `GunFireControlModel.SurfaceSigmas` (static; surface targets only) divides rangeSigma, bearingSigma, predictionSigma, stabilizationSigma by it (2 = twice as accurate), on top of director gain/light/crew/solution and `MaxAccuracyMeters`; all guns, at once (no reload). `AccuracyMultiplier` is the other half: shell scatter (CEP). Air targets (BuildAaErrorBudget) are not touched.
- `LocalControlAccuracy` / `OpticalDirectorAccuracy` / `RadarDirectorAccuracy` (1 each, GUI Guns tab, group Accuracy): `DevCheckPrefix` (prefix of the private `WeaponSystemGun.DeviationCheck`) classifies the gun by `GetFireControlSensor()` (null = local control; `SensorSystemRadar` = radar; else optical) into a [ThreadStatic] `_fcKindMult`, cleared by the finalizer; `FcErrorPostfix` (SurfaceSigmas) divides the four sigmas by `FireControlAccuracy * _fcKindMult`. The kind multipliers therefore act only on real salvos; the general one also on the other SurfaceSigmas callers. Per salvo, at once.
- Director profile options (`WeakDirectorsAccuracy` 1.5, `OpticalDirectorGain` / `RadarDirectorGain` 1, `LocalControlGain` 0.75, `OpticalDirectorMinSolution` / `RadarDirectorMinSolution` 1; GUI Guns tab, group Accuracy): postfix of `SensorSystem.ResolveFireControlProfile` (prefix keeps the `_fcProfileResolved` state) remembers the sensor's own `_fcSolutionGainRate` / `_fcMinSolution` once (ConditionalWeakTable `FcBase`) and rewrites both at EVERY call from that base, so a changed option works at once: for gain < 0.75: gain' = min(gain * m, 0.75) (m < 1: gain * m), min solution by the same factor, then x kind multiplier (radar = `SensorSystemRadar`, else optical). Why: the gain scales range error (1/g^2), bearing (1/sqrt g), solution build speed (~g), the unstabilized factor and the spotting decision, and rule sets differ in scale (game: optics 0.75, radars 1.5-2.5; WW2 pack ww2x: optics 0.11-0.37 median 0.24, radars 0.23-0.60 median 0.36, 9 targeting radars without values get >= 0.75 from `Infer`). `LocalControlGain` sets the static `Globals._gunLocalControlGainRate` (0.6 x value, `ApplyLocalGain`, at start and on every setting change; WW2 directors are worse than local control otherwise). `RangeSigmaPostfix` divides the game's own aim error estimate of `NeedsSpottingFire` (`WeaponSystemGun.GetMeasurementRangeSigma`) by the same accuracy multipliers as the real error, so a more accurate gun does not keep waiting for splashes. Not covered: the prediction term of that estimate; local control builds its solution without gain (faster than a weak director).
- Presets (Guns tab, Accuracy, `PresetBar` in SettingsWindow.cs): buttons Base / Advanced / WW2 fill 10 settings in the work copy (`PresetKeys`, `PresetValues`: WeakDirectorBoost, Optical/Radar gain, LocalControlGain, Optical/Radar min solution, the four error multipliers) and redraw; nothing is stored but those settings, the bar shows a tick when the current values equal a preset (`CurrentPreset`). base: all 1; advanced = the config defaults (weak directors x1.5, local gain 0.75); ww2: weak directors x2, radar gain 1.25, local 0.6, radar min solution 1.25. UI names: gain = "accuracy and solution speed", the four error multipliers = "extra aiming accuracy", min solution keeps its name. Shell accuracy (`AccuracyMultiplier`, `MaxAccuracyMeters`, ammunition table) is not in the presets.
- `AmmunitionFix` (false by default since 11.11): layers: the game's ini < the pack `Release/ammunition_fix.txt` (format of ASE's `hit_effects.txt`: `[ammunition file name]`, `Key=value`; 48 ammunition; keys CircularErrorProbable [Physics] metres and Power [WarheadData]) < the player's values `AlternativeWeaponsControl.ammunition.txt` next to the .cfg (a key stored only if it differs from the pack, or from the game when the pack has none). Harmony postfix of the `AmmunitionParameters(string, int, WeaponSystem)` constructor (also builds shared masters that `Create()` clones with MemberwiseClone; static `_sharedByType`): `_circularErrorProbable = CEP * 0.0148809375` (projectiles only), `_warheadPower`; `_warheadDudPower` (x0.2, missiles x0.5) and `_ammoPoints` follow Power only if they still hold the game's defaults. Applied to ammunition loaded after Apply (mission start); Apply drops the changed shared masters. The encyclopedia still shows the original values.
- Game values shown in the table (`game:`) are read straight from `StreamingAssets/original/ammunition/<name>.ini` on disk (own small parser: `[Physics] CircularErrorProbable`, default 50; `[WarheadData] Power`, default 0), never through the game's layers, because other mods replace the layered files. No file -> "?". Titles come from `ammunition_names` (`LocalizationLoader.OpenVirtualLocalizationFile("language_<lang>", ...)`, first element of the "name,,type,description" line). `default:` = the pack's value (the game's when the pack has none).

## Remembered gun targets (GunTargets.cs, `[Guns] RememberTargets`, on)
- The game hands every new player's order to ALL plain guns with the ammunition (`HandleEngageTasks`, branch for `WeaponSystemGun`) and keeps no trace of the old one. `HetLeave` -> `RememberGunOrders`: orders held by the unit's plain guns (exact type `WeaponSystemGun`, not CIWS; not automatic, not tied to a launcher) go to `GunMems[unit]` (newest first, max 8, one per target+ammunition). `GunTargetsStep` (Update, every 0.5 s): for each gun with such an order (or idle) takes the first entry it `GunCanReach` (range from `_launchRangesInUnity.y`, aircraft limit, `targetIsInFiringArc`) and has the ammunition for; keeps its current target if that is reachable and not older than that entry; `GunTake` sets the engage fields as the game does. An order goes into the list once (`GunSeen`, by task object): all guns hold it, and the guns that moved to an older target hold the older order - re-inserting per gun every frame made the order depend on the last gun and pulled everyone back to the older target. Gone targets drop out; cleared by the tab's Cease (`ForgetTargets`) and by `ObjectBase.CeaseFire` (postfix; also Hold). `GunCanReach` also requires contact (`GetMapVehicle(taskforce) != null` unless `_ignoreIfUndetected`): `WeaponSystemGun.OnUpdate` aborts an order on an undetected target at once, which made the step re-take the gun every 0.5 s (flicker). Not saved with the game. The player's units only.

## Fire zones (Zones.cs, [UI] FireShowsZones)
- `[UI] BottomPanelFire` (on by default, needs FireShowsZones): the bottom weapon panel's `WeaponEntry.Command` calls `AttackingState.TryStart`; prefix/finalizer (`TryStartPrefix/Finalizer`) raise `OurFireDepth` around it (not for waypoint edit, not inside our own Fire) and clear `Pending`, so the state is marked ours (ring hidden). The zones themselves do not need the tab: `BottomZonesStep` (Update, 0.1 s) shows them for the current ours-state of a player's unit (systems = `WeaponEntry.WeaponSystems` of the game's ammunition group, guns included, as the tab's Fire takes them) and ends them; a state with a `Pending` tie of the same unit is left to `CheckTargeting`.
- Zones are shown only for targeting started by the mod's Fire (`OurFireExecute`, `IsOurState`); the game's own Fire keeps its circle. The game draws sectors / range through `WeaponArcHoverManager` (`Hovered` only with Alt); the mod creates its own `HoverInfo` (Unit, Systems, MapRangeInUnity = `_launchRangesInUnity.y`), holds it in `Hovered` in the prefix of `Reconcile` while `CheckTargeting` sees the unit's AttackingState, and clears it at the end. A single pinned launcher shows only its zone.
- The max-range circle of AttackingState is hidden: prefix `set_MaxRangeInLat` stores the real value (ConditionalWeakTable) and passes 0; prefix / postfix of `UpdateBearingPreview` put the real value back for the call.
- 2D map colour (0.8.7): `WeaponArcSegmentViewModel.Render(MapRenderContext)` opens a `ctx.Pie(128)` slot with `ctx.Palette.Stroke(MapColor.FiringArc, thickness)` (the template is an empty Canvas, there is nothing in the UI tree). While the zones are shown `MapPalette.Override(MapColor.FiringArc, red, red)` is set on the MapBase palettes (cached) and restored at the end. Weak red fill: lazy postfix of `Render` adds a second Pie slot (`MapFill.From`), active only while `_zoneInfo != null`.
- 3D: postfix of `WeaponArc3DRenderer.Show` sets vertex colours (colors32) of `_arcObjects` to (235,45,45,0x30) while `_zoneInfo != null`.
- Do NOT patch the map controls (MapEllipse / MapPie / MapPath callbacks), `ThemeDictionarySwapper.ApplyTheme` or `GizmoHost.UpdateHost`: the game crashed at start. `_zoneUnit`: only the unit that started the zones may end them (two unit windows made the zones flicker).

## On Free: unidentified aircraft (FreeAir.cs)
- Flag under "On Tight" in the tab header (ships only; `UnitW.FreeAirSet`: -1 default of the side, 0/1 = player's choice; saved as `AlternativeWeaponsControl_FreeUnknownAir`). Defaults: off for the player's and allied ships (`Fire/UnknownAirDefaultOwn`), on for enemy ships (`UnknownAirDefaultEnemy`).
- Why the game does not shoot unidentified aircraft: `AI.GetPossibleTargetsList` takes a unit only if `IdentifiedAsHostile`. Postfix `FreeAirPostfix` adds aircraft / helicopters from `_processedObjects` that are Unknown on the plot (the true side is not checked), faster than `Fire/UnknownAirMinKnots` (500), nearer than `UnknownAirMaxNm` (20), flying at the ship (angle <= 45 degrees); speed kn = |UnityVelocityVector| / 0.0076554087. The choice on a unit beats the defaults. CIWS checks `CurrentRelationship == Hostile` itself and will not open fire on such targets.
- `Fire/EngageByPlotRelation` (on; UI label "Disable AI cheating"): the game takes a target only if it is hostile on the plot AND its true faction is hostile. `PlotHostilePostfix` adds units hostile on the plot (surface only with AutoAttackSurface), priority `GetEngagePriority`, sorted again. Also works on Tight when "On Tight: engage hostile aircraft" is on (aircraft only); nothing on Hold.

## SAM readiness (WarmUp.cs, WeaponsView WarmButton)
- Button for `WeaponSystemLauncher` with `_vwp._hasWarmUp && _hasWarmUpAmmo` and a magazine; one missile icon per rail position. States: grey (rails empty), amber (loading / warming up), green (loaded and warm). Options: `[UI] SamReadyButton` (true), `SamReadyMinutes` ("SAM readiness limit", 15), `[Ships] SamAutoCharge` (true), `SamAutoChargeRange` (30 nm), `SamKeepLoaded` (true), `SamAnimFix` (true).
- One model: cold (empty rails) -> loading -> warming up (the game's reload with missiles ON the rails) -> ready. Real launchers warm the missile on the rail; the game's own order flow is the same. ### Orders loaded from a save are "newer" than new orders (fixed, no option)
Trace 02:05-02:07 (Leander, director destroyed): the player's Fire on Miyuki stayed in `_currentEngageTasks` for minutes, the 6in guns kept the order loaded from the save (Sakawa) and the order watch printed `busy with Sakawa (order, newer)`. Cause (game): `GameTime.LoadStateFromFile` reads MissionElapsedTime and discards it, while `EngageTask.CreateFromFile` restores the saved `CreationTime`; HandleEngageTasks breaks off a gun for a player's order only if `!(gun.taken.CreationTime >= order.CreationTime)`. A loaded order whose creation time is ahead of the clock therefore can never be replaced. Fix: `FixFutureTasks` (called from `HetEnter`, i.e. in the game's handling of the unit's orders, with no timer; only for the player's units whose order list is not empty) sets such creation times (list tasks and mounts' taken tasks) to clock-1 s and traces `creation time ahead of the clock (A vs B)`. The order-watch lines also print `clock=` and `order born=`.

### The player's order has priority 0
`OrderFirst` (AttackTask.OnExecute postfix): the engage task of a player's order gets `_priority = 0` and moves to the front of `_currentEngageTasks`. The game uses the target class (a ship = 10), so the AI's tasks (1..5) were processed before it and could take the guns over (`AI`: a task takes a mount when `priority < mount._engageTaskPriority`); with 0 the AI can never interrupt a gun that holds the player's order. Orders loaded from a save keep their saved priority.

### The player's orders: priority 0 whatever way they are made
A click on a contact with a unit selected (UnitSelectedState.AutoAttack -> AI.AutoAttackByClick) makes `new EngageTask(ammo, target, unit, salvo)` with the default priority 1000 (the lowest, appended last) and picks ONE gun ammunition (SelectAmmunition: the best one) - a ship with two gun calibres sends only one of them. `HumanFirst` (in `FixFutureTasks`, i.e. in the handling of the unit's orders) sets priority 0 and moves to the front every non-automatic task of a player's unit; `OrderFirst` (Fire from the tab) is the same earlier. `ClickEngagesAllGuns` (default on, GUI Guns tab): postfix of `AutoAttackByClick` adds a task for every other gun ammunition that reaches the target (min/max range only; the firing sector does not matter). The extra tasks get creation time 0: HandleEngageTasks breaks off the guns of another target for a WAITING order newer than the guns' order, so with two targets clicked one after the other the waiting extras of the first target kept tearing guns off the second (the sides no longer fired at different targets). Creation time 0 = older than all orders: an extra takes only free guns. Why the game picks one: SelectAmmunition takes the longest-range ammunition that has a mount usable NOW (`isWeaponSystemUsable` with sensors: a destroyed director = `HasFreeGuidingSensors` false, or a gun reloading), so on HMS Leander with the director destroyed the 6in were skipped and the 4.5in chosen.

### Guns on local control fire rarely (LocalControlKeepsFiring, default on)
WeaponSystemGun.fire holds every next shot (`NeedsSpottingFire`, only with DM._gunsDeviation, naval mode) until the previous shell has landed (`_canFireSpotShotTime = now + flight time`) while `_solution` < 0.95 and no round-tracking sensor. A gun with associated sensors sets `_solution` to the best working sensor's solution every check, and the splash-spotting bonus is added only to working sensors - with a destroyed director both are 0, so the solution stays 0 for ever: one shell per flight time (HMS Leander's 6in, trace 02:16: last salvo 23-43 s ago, flight 23-57 s). `SpotPrefix` returns "no spotting needed" for the player's gun when `GetFireControlSensor()` is null (no working director = local control). Accuracy is untouched (the game's gain 0.6 and a zero solution still make the aim poor). A gun with no associated sensors at all builds the solution itself (SensorUtils.BuildSolution) and is not stuck.

## Performance notes
- `SensorSystem.ResolveFireControlProfile` is called by the game for every director of every gun on every `GetFireControlSensor` (it returns at once once resolved). `FcProfilePostfix` therefore does nothing when the profile was already resolved and the sensor was last adjusted under the current `_fcEpoch` (bumped by `Cfg.SettingChanged` and the Mods-menu tick); `FcBase` holds `{gain, minSolution, epoch}`.
- The .cfg is not watched at all (no polling, no `FileSystemWatcher`): a file edited outside the game is read at the next start; the mod's own window saves it.
- `R.Call` keeps `GetParameters()` per method (it copies the array on every call).
- "Sensors Offline" / "Sensor inoperable" are shown only for a launcher that needs a director (`NeedsSensors`, decided once per launcher and cached in `WsCache`): by the game's own rule `ObjectBase.DoesEngageRequiresSensor(ap, null)` (projectile, SARH, radio command) or SARH for vessel/land targets, over all the launcher's ammunition; guns are exempt (local control, `FireControlMode.Manual`). RBU, bombs, depth charges, torpedoes and fire-and-forget missiles therefore show no sensor status; the game's own "Sensors Offline" text (`GetStatus`) is replaced for them by Ready / Engaging.
- `LsSync` (BigGunsLocalSolution) runs for every gun on every `OnUpdate` / `AlignTurret`: the eligibility (`LsEligible`: shooting mode, ammunition, the game's director search) is cached in `LsBox` per target and refreshed 4 times a second; only the `_solution` write is per call.

## Strict EMCON: gun-only radar stations as optical directors
- `OpticalStation(sensor)` (GunFixes.cs, decided once per sensor, cached): a `SensorSystemRadar` whose every weapon (`_vwp._associatedSensors` contains it) is `_weaponType == Gun`. Missile/CIWS directors are not (they illuminate or command; optics cannot).
- Such a station is not disabled by Strict EMCON (`RadarsOff`) and may be enabled (`EmconEnablePrefix`). `Trimmed(sensor)` = optical station and its unit has `StrictEmcon`. `RetrimStations(unit)` (toggle click) bumps `_fcEpoch` and re-resolves the stations; load sets `_trimAny`.
- `FcProfilePostfix` (reapplied when `_fcEpoch` changes) for a trimmed station: gain = `Lerp(localControlGain, radarGain, StrictEmconOpticalShare/100)` (local = `Globals._gunLocalControlGainRate` after `LocalControlGain`), min solution with the optical multiplier, `_fcTracksRounds = false` (optics do not follow shells in flight; splashes stay observable), and `Radiate(sensor, false)`: `_radar._rp._peakPower = 0` (RadarParameters is per sensor; `RadarCalculator.getSignalStrength` lists an emitter only when the signal > 0, so ESM does not hear it; the station stays IsOn and a gun director needs only IsOn + a free channel). Restored from `PeakBase` / `FcBase` when Strict EMCON ends. Why a rule on the numbers: the game's local control is 0.6 (mod default 0.3) - a plain 50% of the radar gain would put most directors below local control (game: 49 of 83 radars below 0.6, WW2 pack: 69 of 69 below 0.6, 59 of 69 below 0.3).
- Night: `TrimLightPostfix` (`SensorSystem.GetFireControlLightFactor`) returns the sunlight like `SensorSystemVisual` does (night vision level 0); `TrimSplashPostfix` (`WeaponSystemGun.CanObserveFallOfShot`): in the dark a splash is seen only when a real (not trimmed) working radar is associated.
- Range: the game's gun fire control does not use the director's range at all (`TryToAddTarget` needs IsOn and a free channel; `SensorUtils.BuildSolution` uses the distance to the target only), a visual sensor's range limits only its own contacts. Nothing is cut by the game, so the mod does it: `TrimRangePostfix` on `WeaponSystemGun.GetFireControlSensor` gives a trimmed station up for a target beyond the range of a Kind=Visual sensor (`SensorUtils.CalculateVisualRange(base, target, nightVision 0)` and `UnitSensorCache.VisualHorizon` from the station height, as `SensorSystemVisual.CheckObjectDetection` does; the unit has no night vision): the next director (`FireControl.ResolveBestDirector` over the rest), else local control. Evaluated on each call, only for a trimmed station with a target.
- Texts: the directors window shows `dir.optical` (on, radar off: optical mode) and the gun tooltip `gt.trimmed` for a `Trimmed` station.
